# Can a newer frozen Qwen judge detect a false correction?

27 November 2026 · Development extension specified after the original seed-17 comparisons and before inference with these judges. The original held-out analysis has its own checkpoint manifest and decision rule. [Original preregistration](preregistration.md) · [Run inventory](run-inventory.md)

The first experiment changed which judge rewarded a trainable solver. This follow-up first changes the weights inside all three **frozen** judge calls and fixes the solver's written answers. It asks whether an auditor can identify a corrupted number while retaining the correct verdict on the solution. Only a separate online comparison can measure what a solver learns from that auditor. The proposed mechanism and the alternative that the newer model merely becomes better at arithmetic make different predictions on evidence-only twins. ## Cases, endpoints and decision

Before any frozen-judge inference, inspection found two additional locally installed Q4_K_M text artifacts. Run the 9B and 4B Ollama-packaged weights first, through the same CUDA llama.cpp runtime and the native upstream template. These deployment replicates get separate IDs, the full screening cohort and their own raw results. The registered screen and winner selection still use the four specified Hugging Face configurations. A tag or model family name does not identify a conversion, so reproducibility uses the exact registry blob digest. [Ollama 9B artifact](https://ollama.com/library/qwen3.5:9b) · [Ollama 4B artifact](https://ollama.com/library/qwen3.5:4b) · [Immutable model digests](../src/study/frozen_models.py)

The initial allocation covered frozen-judge inference and independent confirmation. The owner subsequently authorized the two solver arms specified below.

1. **Natural replay.** For each feasible model, give the complete chain the same 32 archived starting-solver traces. J2 reads that model's actual J1 report and J3 reads its actual J1 and J2 reports. Record each depth's verdict and whole-report accuracy, false accepts, false rejects and malformed reports. Count J2-to-J3 fixes and harms on the same responses. Any gain here leaves the saved solver answers fixed.
2. **Balanced replay.** Use 32 distinct problems from the confirmed arithmetic family, positions 96 through 127 (zero-based) of the deterministic development-confirmation stream. On each, compare a correct trace with one incorrect intermediate step. Each model sees the same two traces and generates its own chain. Report balanced solution-verdict accuracy at every depth. Its denominator includes both traces for every problem.
3. **Evidence intervention.** On the same 32 problem IDs, use the existing evidence-twin generator, alternating valid and invalid solver solutions and sound and flawed J1 reports. Both J2 twins contain the same solution verdict. J3 must return both complete checker-correct records, including the first bad field and its replacement. Score both visible twins and score both again with the J2 evidence masked. All model inputs are independent requests. Ground truth enters only scoring and the construction of the controlled examples. The primary offline endpoint is visible whole-pair accuracy. Its denominator is the number of problem pairs. [Twin constructor](../src/study/judging.py) · [Independent field labels](../src/study/records.py)
4. **Fresh confirmation.** Rank feasible newer candidates by whole-pair accuracy, then balanced J3 verdict accuracy, then total measured generation time on the screen. Run the first-ranked candidate and the same-runtime control on 64 distinct confirm-stream problems at indices 256 through 319. Use paired resampling by problem, jointly resampling both balanced traces or both twins. Report the two differences with descriptive 95% percentile intervals from 10,000 resamples. Repeated use of the original 32 natural traces is diagnostic. The fresh confirmation is the selection-independent comparison. Neither phase reads the original sealed test population.
5. **Conditional solver training.** If the winner strictly exceeds the same-runtime baseline on both confirmation point estimates (whole-pair accuracy and balanced J3 verdict accuracy), train fresh seed-17 Qwen2.5-1.5B solver adapters with either its J2 or its J3 as the frozen reward. Keep initial solver, four completions, 256 updates, prompt order and generation ceilings matched. Save all reward vectors and measure whether the solver improves on the original common development questions. The trained solvers must be evaluated directly. If either offline comparison fails to improve, record the gate outcome and the two unstarted online arms. Evidence for the auditing hypothesis also requires visible pairs to outperform their masked copies. An interval spanning zero is inconclusive about a population-level improvement. Every model has the same output format and input evidence. Native templates can tokenize that evidence differently. Compression may affect arithmetic and evidence accuracy, particularly for the 27B configuration. Report fit failures, selection, all candidates, all outcomes and costs even if no model improves. ## Runtime correction before comparing scores

The balanced replay changes one numbered value. On the two-step family, its fixed error index alternates between the first and final step. The per-model audit reports both counts. This implementation detail narrows the interpretation of the protocol's phrase “one incorrect intermediate step.”

The initial 9B deployment pilot revealed that the chat endpoint returned an empty reasoning wrapper from the prompt template as part of the assistant message. The strict grader treated the wrapper as output, and successor prompts included the wrapper. The archive retains all delivered messages. This pilot supplies no accuracy estimate. For every scored run, explicitly render the native non-thinking template and request its raw completion. Store the rendered prompt, actual generated token IDs and generated text separately. Forward and strictly score only the generated text. Rerun every affected chain from its first judge. The checker, problem assignments, generation budget and model-selection rule stay fixed. ## Sustained 27B throughput amendment, 27 November 2026

The original four-call timing pilot passed for the IQ1_M file. The same deployment later took more than the existing 30-second ceiling on consecutive scored requests. Loading the identical model again reproduced the slowdown. This observation motivated an amendment **after the IQ1_M screen began and before inference with IQ1_S or the independent confirmation set**. Its trigger uses timestamps, call identities and wall durations. It does not inspect answers or grades. [Original 27B calls and fit records](../results/new-judges/q38-27b) · [Eligibility check](../src/study/frozen_latency.py).

At a completed case boundary, three consecutive scored requests above 30 seconds trigger one reload of the identical 27B file. A subsequent slow scored request that leaves three consecutive calls above the ceiling confirms persistence if the preceding load also ended with three slow calls. Preserve all partial records without estimating cohort accuracy. If the file was larger than the smallest registered compression, start a separate IQ1_S screen from the first prompt. Apply the same model, problem, timing, CUDA placement and scoring checks. Keep costs and responses in separate directories. Repeat the same sustained-throughput check on the smaller file and any 27B confirmation. [Reproducible campaign](../src/study/frozen_suite.py).

Report which original completed model wins when the partial screen is excluded and which model wins when the separate IQ1_S screen is eligible. The independent confirmation evaluates the latter selection against the same-runtime control. An incomplete IQ1_M screen leaves that file's accuracy unresolved. [Run inventory](run-inventory.md).
